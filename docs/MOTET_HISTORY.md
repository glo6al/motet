# Durable Motet history backend

Memory recording now also captures new Motet requests and their sanitized answers locally. Nothing imports earlier conversations or browser storage. Recording remains off by default. Enable, pause, disable, retention and deletion use the existing Memory controls. Earlier records are read-only, untrusted evidence; reading them never calls a model, delivers a message, retries work, applies suggestions or authorizes a control.

## Storage and policy

Schema 4 adds `officer_entries`, `officer_seen` and `officer_gaps` to `deck-log.sqlite3`. Schemas 1–3 upgrade additively; unknown versions are refused. Existing private-directory/file verification, POSIX permissions, Windows ACL checks, SQLite locking, rollback journal, secure deletion and 64 MiB database page cap apply. No dependency or service is added. Entries are limited to 5,000 and retained for the configured 1–365 days. A bounded 100,000-ID HMAC deduplication ledger contains no prose; at capacity new recorded requests are refused rather than silently evicting retry protection. Coverage markers retain at most 100 rows. Source and Motet rows share the storage cap, so recording may stop when storage fills. After installing this update, restart Motet to load the new server routes; an already running server keeps its earlier code. The schema upgrade runs when the updated archive opens.

Questions and answers use the existing bounded prose sanitization and exact current capability redaction. Recognized credentials, code, paths and payloads are removed; arbitrary prose can still contain unrecognized private information. Answers are limited to 8 KiB, questions to 4 KiB. Stored source metadata contains bounded identities, fingerprints and observation timestamps only, with no source body, signed receipt, browser capability, native snapshot or preview/file body. Names and raw action input are excluded. Usage is metadata only, never provider response bodies.

Any source deletion or expiry conservatively deletes **all** durable Motet prose in the same archive lifecycle, because an answer may depend on uncited inputs. Explicit deletion retains only hashed retry markers and bounded coverage metadata. This can remove answers earlier than their own retention deadline. Enabling an exclusion likewise erases all Motet prose. While **any** chat/project exclusion exists, Motet history does not capture any question or answer: a stage or station question can inspect other subjects, so the selected scope cannot prove safe exclusion. Existing retained room-event recording continues to honor its own exclusions.

A durable privacy-cleanup marker suppresses reads and duplicate prose after failed exclusion cleanup, across restart and removal of the exclusion, until cleanup succeeds. Policy changes rotate the capture epoch. Late answers cannot restore an erased row or cross an epoch boundary. Duplicate request IDs with the same question and scope return a read-only prior result without executing; changed text or scope conflicts. HMACs distinguish original question text even where the safe stored text is redacted. Deduplication remains after prose deletion and expiry. Requests made while recording is off are not imported or retrospectively deduplicated by this history feature. The existing messaging/control ledgers retain their own idempotency rules.

Writes commit synchronously under the archive lock. No archive lock spans a model/transport call. Shutdown uses the existing Deck Log close lifecycle. In-flight requests surviving restart become completion-unknown; recorded delivery outcomes retain their original observation time and do not establish current delivery or completion. Outcome observers update only existing recorded IDs and never create entries from old messaging records. A storage failure cannot change an authoritative transport outcome or trigger retry; history is reported unavailable or not recorded.

## Read contract

The optional workspace Motet desk reads these routes through its explicit **Recorded days · UTC** control. This viewer has separate temporary state and preserves the live conversation, draft and focus on return. Archived actions and source metadata are inert. Historical duplicate responses from `/ask` are also excluded from live model replay and browser conversation storage. No recorded day is represented as complete, and unavailable or invalidated reads clear the previously displayed prose.

Both routes require the existing host/origin checks and `X-Live-Room-Key` owner header. Responses are private `application/json`, `Cache-Control: no-store`. They expose no new MCP tool or filesystem lookup. Only GET is supported. Unknown/repeated/malformed fields return 400; missing/wrong auth returns 403; unavailable archive initialization returns 503. A readable endpoint whose store fails returns a result with `status: unavailable` and no records.

- `GET /history/officer/days?limit=50&cursor=2026-10-31`: available retained UTC days, newest first. Optional cursor is an exclusive day; limit is an integer 1–100.
- `GET /history/officer/day?day=2026-11-01&limit=50&cursor=<entry-id>`: required exact ISO calendar day, newest first, stable timestamp/ID ordering. Cursor is an existing entry ID belonging to the selected day; deleted, expired and mismatched cursors return 400. A cursor is navigation data, never authority.

All day boundaries are **UTC**, including DST transition days. UTC days always span 86,400 seconds. Browser-local or host-local grouping must not be assumed. The response includes `timezone`, `start_at`, `end_at`, source timestamps, `recording_started_at`, bounded coverage markers and `recording_now`. The backend supports Windows without relying on an installed IANA timezone database; existing platform restrictions on Motet execution remain unchanged.

Top-level `status` is `partial`, `not_recorded`, `expired` or `unavailable`. `complete` remains false: retained observations do not prove whole-day capture, including offline/policy gaps. `page_complete` means the requested page exhausted matching retained rows, including an empty result; it does not mean the day was fully recorded. `cursor` is null on the final page. Empty partial results, unrecorded pre-start days, expired days and unavailable storage are distinct. Coverage markers describe observed policy/erasure/restart boundaries; they are bounded and cannot reconstruct every missing interval.

Each entry includes stable `id`, `request_id`, `started_at`, `updated_at`, `scope`, safe `question`/`answer`, `selected_model`, `actual_model` when a provider response supplied it, `redacted`, `state`, `verification`, `partial`, `warnings`, safe `usage_tracking`, and `historical: true`, `read_only: true`. Selected model is not the provider's actual returned model. Certainty `recorded` describes the fact of recording, not truth of model-written prose. Material answer warnings are bounded and sanitized.

Actions are inert records with `kind`, optional `agent`, control `action`, correlation ID, `outcome`, `observed_at` and qualification. Queued, awaiting reply, answered, delivery unknown, expired, failed, rejected, acknowledged, interrupted and no-op remain distinct. Queue acceptance and acknowledgement do not prove completed work. Screen suggestions are recorded only as suggestions, with no executable payload. Their application in a browser is not observed by the server and remains unsupported.

Source references contain ID, optional fingerprint, known retained-source UTC timestamps and certainty, plus lookup status: `retained_identity_exists`, `removed`, `unavailable`, or `stale` for process-local observations. Existence does not freshly verify the narrative. A missing retained source suppresses derived answer text; deletion/expiry normally erases the entire entry first. No historical signed proof is returned or accepted as a current receipt. Read-only historical text must never be submitted as an authenticated assistant replay.

## Overview limits

`overview.recorded_questions` counts retained recorded question entries for that UTC day. It is a lower bound, not a complete daily total. Empty/unavailable history returns null rather than claiming zero. `daily_officer_estimated_usd` and `skills` are null. Existing Motet usage already tracks API attempts, including intent and answer rounds; its public summary uses rolling lookback periods rather than exact UTC calendar days. This patch does not duplicate accounting or mislabel rolling estimates as daily invoices. A future interval query over that existing ledger could supply a qualified daily Motet estimate. Missing/partial usage stays unknown; neither organization billing nor skill availability is supplied by these routes.
